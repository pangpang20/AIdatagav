# 业务需求管理系统子页面与操作需求细化

## 1. 范围与入口

业务目标：把部门诉求归入项目，分派协作任务，并跟踪咨询的受理情况。本文件补充[模块需求正文](./需求说明.md)，按真实菜单层级分开说明对象、维护页面和前置条件。

页面字段和操作结果来自当前账号的只读取证。功能建议与页面事实分开；业务保存、删除、审批、授权及任务执行均未验收。

### DRMS-500 需求看板 → 需求看板

**业务目的**：使用者在“需求看板 → 需求看板”处理对应对象；与其他菜单分别保留查询条件、对象标识和处理状态。

【页面观察】实际路径为`/drms/kanban`。

**用户操作与系统响应**：

1. 从“需求看板 → 需求看板”进入目标页，先核对当前部门、空间及对象范围。
2. 当前样本没有可用于完整定义检索条件的输入，不能推测支持全文或模糊查询。
3. 该页不按普通表格定义；实际卡片、图形或前置提示以来源截图为准。
4. 未取得可独立识别的行内操作；不推定存在维护能力。

【页面观察】采样中出现“暂无数据”；它可能属于列表、下拉或子表，须结合截图定位。不能据此宣称整个模块无数据，也不能用空列表证明查询失败。

【拟定需求】业务依赖：项目与需求的归属、需求启动/关闭条件、任务分派与完成的责任人，以及咨询转需求的关系需逐项确认。

## 5. 主要流程

### 项目、需求与咨询分别办理

【页面观察】需求新增页按需求信息、基础数据、数据库信息、添加附件分步组织；当前取得第一步。需求标题50字符、业务用途和预期应用成效各500字符是客户端上限，所属项目有必填星标，申请人和申请部门禁用。咨询新增另有标题、发起部门、发起人、附件、需求描述和预计应用成效，不能直接复用需求表单。

【拟定需求】申请人先确定所属项目，再说明用途与预期成效。拟定以需求标识保存各步骤草稿，返回上一步保留已填内容；项目失效、权限变化和草稿并发需明确提示。咨询是否可转为正式需求、转入后的字段映射和重复关联由产品确认。

【待确认】后三步内容、步骤间校验、附件规则、保存草稿与正式提交的区别及状态转换尚缺证据；不得将第一步必填项作为完整需求定义。

## 7. 待确认与限制

- P0：各对象的读写权限、唯一性范围、状态转换、引用保护、并发和保存结果契约。
- P0：第2节未取得可用正文的目标；维护页后续标签、步骤、类型分支及无可用记录的详情。
- P1：查询匹配与默认条件、空值和排序、分页恢复、动态候选关联、导入失败和取消策略。
- 删除：本轮不自动点击可能直接删除数据的入口；已有确认框证据保留于主文档，未取得确认页的对象继续待核实。
- 任务：可以打开配置，不执行生成、测试连接、发布、调度、重跑、启停或服务调用。
- 开发边界：可实现有依据的界面结构和标明模拟状态的原型；生产写入、接口、算法与完整状态机仍需产品及技术确认。
